# 14. TOGETHER LISTENING — CRITICAL

Her Music uses a server-authoritative synchronization model.

```text

    ↓
```

```text

```

# 15. IMPORTANT SYNCHRONIZATION CORRECTION

Do NOT blindly trust each browser's local clock.

Do NOT assume that:

```text
Date.now()
```

on Client A and Client B are equivalent.

Do NOT describe a Supabase Broadcast payload as automatically providing a trusted authoritative server timestamp unless the implementation actually obtains that timestamp from a trusted server-side source.

The system should establish a server-time reference.

Possible architecture:

```text
                Trusted Server Time
                       |
              server timestamp
                       |
        +--------------+--------------+
        |                             |
     Client A                      Client B
        |                             |
     clock offset                  clock offset
        |                             |
        +--------------+--------------+
                       |
                 sync calculation
```

If the existing architecture uses Supabase Edge Functions, PostgreSQL, or another trusted server-side mechanism, use that existing infrastructure.

Do not introduce an unnecessary new backend if the current infrastructure can provide the authoritative timestamp.

# 16. TOGETHER PLAY EVENT

When the host presses PLAY:

The authoritative state should conceptually contain:

```text
track_id
position_seconds
state_changed_at
is_playing
sequence_number
```

The receiving client calculates the expected position using the authoritative timeline.

Conceptually:

```text
expected_position =
    position_seconds
    +
    elapsed_authoritative_time
```

For a playing track:

```text
elapsed =
    authoritative_now - state_changed_at
```

Then:

```text
target_position =
    position_seconds + elapsed
```

The guest should seek toward that position.

Do not repeatedly hard-seek every few milliseconds.

---

# 17. DRIFT CORRECTION

Implement controlled drift correction.

Example strategy:

```text
drift < 100ms
    → do nothing

100ms–300ms
    → gentle correction

300ms–1000ms
    → stronger correction

> 1000ms
    → explicit seek/resynchronization
```

Use thresholds appropriate to the actual audio engine after testing.

Avoid constantly fighting the user's player.

The system should feel synchronized rather than visibly jumping.

---

# 18. RACE CONDITIONS

Protect against:

```text
PLAY
PAUSE
SEEK
NEXT
PREVIOUS
```

arriving out of order.

Every synchronization event should have an ordering mechanism such as:

```text
sequence_number
```

or an equivalent monotonic event identifier.

Ignore stale events.

Example:

```text
event 101
event 102
event 103
```

If event 101 arrives after event 103:

```text
IGNORE 101
```

Do not allow old network messages to overwrite newer state.

# 19. JOINING A ROOM

Do NOT simply start from position 0.

Guest calculates:

```text
current expected position
```

and begins playback there.

The guest should visually transition into synchronization instead of abruptly jumping around.
